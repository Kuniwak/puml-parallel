# PlantUML Interface Parallel

A Go tool for composing multiple PlantUML state diagrams in parallel with synchronization events, following CSP (Communicating Sequential Processes) semantics.

## Overview

This tool takes multiple Composable State Diagram files and composes them into a single parallel state diagram with specified synchronization events. The composition follows CSP interface parallel semantics.

## Installation

Download binaries from [Releases](https://github.com/Kuniwak/puml-parallel/releases).

## Tool index

`csdfhelp` prints the help of every tool in this repository as one Markdown
document, so a coding agent (or a newcomer) can learn the whole toolbox in one
call. `-short` narrows it to a one-line summary per tool.

```console
$ csdfhelp -short
$ csdfhelp
$ csdfhelp csdfparse csdfevents
```

With no argument it shows every tool but `csdfhelp` itself; with tool names, only
those, `csdfhelp` included. For a command group such as `csdfreplcmd` it also
expands each subcommand's own help.

## Usage

```console
$ csdfparallel [--sync channel1;channel2;...] <file1.puml> [file2.puml] ...
```

### Options

- `--sync`: Semicolon-separated list of the channels to synchronise on (interface
  parallel). An edge on one of them is taken by both sides together, with the same
  number of fields. A field sent (`!y`) on one side is named by that side, and the
  receiving side reads it: `c!y ‖ c?x` is `c!y`. A field both sides receive is
  named as the left side does. Where a side names a field otherwise, each of its
  clauses is read through a renaming, `@[x := y] …`, so no clause is rewritten
  (see [SYNTAX.md](./docs/SYNTAX.md)). Two sides sending one field
  synchronise only where the two values are equal: `c!y ‖ c!z` is `c!y` with the
  guard `@eq(y, z)`.

### Examples
```console
$ csdfparallel -sync 'insert;showAvailable;showPurchasable;choose;drop' ./examples/user.puml ./examples/vendormachine.puml
```

## Input Format
The tool accepts PlantUML state diagram files in a specific Composable State Diagram format. See the [SYNTAX.md](./docs/SYNTAX.md) and `examples/` directory for sample input files.

Inputs may be either `.puml` text files or `.png` images generated by PlantUML (`plantuml -tpng`). For PNG inputs, the embedded source is read from the `plantuml` text chunk written by PlantUML. The same applies to `csdfparse`, `csdfparallel`, `csdfhide`, `csdfcomp`, `csdfevents`, `csdfrepl`, `csdfsort`, `csdflint`, `csdflivelockfree`, `csdftracechk`, `csdftranstable`, `csdfrefinement`, `csdfpromote`, and `csdfreplcmd session new`.

`csdfparse` reads a single diagram. A file argument, a `-` argument, and stdin are all equivalent:

```console
$ csdfparse diagram.png
$ csdfparse < diagram.png
$ csdfparse - < diagram.png
$ csdfparallel diagram1.png diagram2.puml
$ csdfrepl diagram.png
```

`csdfparse` writes one JSON object followed by a newline, `"version": 3`
of the shape `core.DiagramDoc` (`csdf/core/json.go`): the `states` in order,
their `labels` (only those labelled apart from their ID) and `vars`; the
start state `init`, its post `init_post` and `init_line`; the `edges`, each
with its `channel`, its `fields` (each a `dir`, `?` or `!`, and a `name`), its
`guard`, its `post` and its `line`; the end edges `ends`; the assume notes
`assumes`; and `families`, for a diagram `csdfpromote -format json` writes
the family of each map: the `map`, its `key` (the ID parameter of the
promote directive, whose type, named like it or through `TYPEOF`, keys the
map), the local `states` in order, the local
start state `init` among them, which is absence, and the `vars` of each local
state, the fields an instance there holds (empty for a diagram `csdfparse`
reads, which no promotion made). Version 2 added `families` and version 3
the `key` of each; a reader refuses any other version, so a JSON written by
an older release is written again. A clause is a list of its conjuncts, each a tagged union with a
`kind`: an `atom`, its text as it holds it (`pieces`), the argument each hole
reads (`holes`) and the terms they stand for (`args`); a `builtin`, its `op`
and `args`; or `exists`, the `type` it ranges over and its `body`, where the
variable it binds is the term `{"kind": "bound", "index": 0}`. A term is
`free` (`name`, `primed`), `bound`, `index` (`map`, `key`), `field` (`of`,
`name`) or `app` (`fn`, `args`). An edge's `label` and an atom's `text`,
`primed` and `function` (the name of the environment function it denotes)
are derived from the rest, for a program that hands atoms to a glue. A
diagram that still holds promotion directives is refused; run `csdfpromote`
first.

```console
$ csdfparse < examples/valid/skip.puml
{"version":3,"name":"","states":["s0"],"labels":{"s0":"SKIP"},"vars":{"s0":[]},"init":"s0","init_post":[],"init_line":5,"edges":[],"ends":[{"src":"s0","guard":[]}],"assumes":[],"families":[]}
```

## Hiding

`csdfhide` hides channels of a single CSDF diagram following CSP hiding semantics
(`P \ {|c|}`): every edge on a hidden channel becomes an internal `tau`
transition, whatever its fields. A hidden field is a value the `tau` chooses
(`c?x` hidden is `⊓ x. τ`): a field the guard and post read through a hole
(`$x`) is bound by `@exists` in both, the guard `g` becoming `∃x. g` and the
post `∃x. (g ∧ p)`, so that the two agree on it
([CLAUSE_DESIGN.md](./docs/CLAUSE_DESIGN.md)). Until fields carry their
types, the bound field ranges over the type named like it, which is why it
prints as `@exists(x : x) (…)`. The result is printed as PlantUML.

```console
$ csdfhide -channels 'sync' examples/valid/in.puml
$ csdfparallel -sync 'sync' examples/valid/in.puml examples/valid/out.puml | csdfhide -channels 'sync' -
```

Channels that do not occur in the diagram are ignored. A file argument, a `-`
argument, and stdin are all equivalent.

## Promotion

A system built from many instances of one thing — an account per customer, a
trade per order — collapses, written as one diagram, into a single state with a
bundle of self-loops over a map from instance IDs to local states. That form is
what the checkers want and no reader wants. So the author writes the diagram of
*one* instance plus a few directives, and `csdfpromote` generates the global one.

The directives are spelled in PlantUML's own syntax — a `<<promote>>` composite
state per map, a note per `sync` or `constrain` — so the hand-written global
diagram still renders, and the picture shows the promotion.

```console
$ csdfpromote examples/promote/TRADES.puml
$ csdfpromote -lint-only -Werror examples/promote/TRADES.puml
```

Every predicate of the expansion is its clauses joined by the connective ` ∧ `
(see [SYNTAX.md](./docs/SYNTAX.md)): the generated ones are builtins
(`@in`, `@at`, `@frame`, …), and the author's are copied with a local
variable `v` of the instance `x` of the map `m` written into their holes as
`${m[x].v}`. `-template` glosses the builtins in a line comment above each
edge. `-format json` writes the expansion as JSON instead, as `csdfparse`
prints a diagram, its clauses as formulas, with the family of each map (its
local states and the variables each holds, `families`): the shape `csdfbmc`
reads.

The PUML expansion is read by `csdflivelockfree`, `csdfrefinement`,
`csdftracechk` and `csdftranstable`.

```console
$ csdfpromote -format json examples/promote/TRADES.puml
```

Every other tool refuses a diagram that still holds directives, and says to run
`csdfpromote` first. See [Promotion](docs/PROMOTION.md) for the semantics, the
local-diagram contract, and the diagnostics.

## Composing a whole system

`csdfcomp` composes every component of a system in one go: it reads a
*composition tree* — a JSON process expression built from `REFER`, `HIDE` and
`INTERFACE_PARALLEL` nodes — and prints the composed diagram as PlantUML. This
is the diagram that is checked for stable-failures refinement against a
top-level specification. It reads the clause syntax, and a `HIDE` and an
`INTERFACE_PARALLEL` are exactly `csdfhide` and `csdfparallel`, so the tree
above writes what `csdfparallel -sync sync in.puml out.puml | csdfhide -channels
sync -` writes.

```console
$ csdfcomp examples/valid/in_out_tree.json
$ csdfcomp -base examples/valid < examples/valid/in_out_tree.json
```

```json
{
  "op": "HIDE",
  "proc": {
    "op": "INTERFACE_PARALLEL",
    "sync": ["sync"],
    "procs": [
      {"op": "REFER", "path": "in.puml"},
      {"op": "REFER", "path": "out.puml"}
    ]
  },
  "channels": ["sync"]
}
```

Relative paths of `REFER` expressions are resolved against the directory of the
tree file, or against the current directory when the tree is read from standard
input; `-base` overrides both. See
[COMPOSITION_TREE.md](docs/COMPOSITION_TREE.md) for the full format.

## Diagram name

The optional name on the `@startuml` line (`@startuml VendingMachine`) carries no
meaning, but it is kept: parsing retains it and every tool that prints a diagram
writes it back, so `csdfsort` and `csdfhide` round-trip a hand-written
name.

`csdfparallel` and `csdfcomp` build a new diagram out of several inputs, so
instead they record the command that generated it:

```console
$ csdfparallel -sync 'sync' examples/valid/in.puml examples/valid/out.puml | head -1
@startuml auto-generated-by: csdfparallel -sync sync examples/valid/in.puml examples/valid/out.puml
```

Arguments are quoted the way a POSIX shell needs them, so the recorded line can
be pasted back to reproduce the output.

## Canonical order

Every tool that prints a diagram prints the same bytes for the same input, so
committed outputs do not accumulate reordering noise in diffs. `csdfparallel`
and `csdfcomp` explore their input through maps and so order their
transitions canonically; `csdfhide` only renames events and so keeps the order
of its input.

`csdfsort` applies that same canonical order to a hand-written diagram without
changing its meaning: states are ordered by id, transitions by source, event,
destination, guard, then post. The start edge stays first and the end edge last.
The declaration order of the state variables is authored meaning, so it is
preserved.
It prints the diagram in the same order and rendering as `csdfhide`, clauses in
the formula syntax of [SYNTAX.md](./docs/SYNTAX.md) included; a clause in the
old syntax (`@opaque`, a renaming `@[from := to]`) is refused with the reader's
error.

```console
$ csdfsort examples/valid/client.puml
$ csdfsort < examples/valid/client.puml
$ csdfsort - < examples/valid/client.puml
```

A file argument, a `-` argument, and stdin are all equivalent.

## Linting

`csdflint` checks diagrams and writes what it finds as a TSV table with the
columns `file`, `start_line`, `end_line`, `rule`, `severity` and `message`. It
exits 1 when anything is an `ERROR` and 0 otherwise, so a `WARN` or a `HINT`
never fails a build. It reads clauses as formulas (`docs/CLAUSE_DESIGN.md`), as
`csdfparse` does, so the old `@opaque` and `@[from := to]` are reported as
`syntax-error`.

```console
$ csdflint examples/valid/client.puml
$ csdflint examples/valid/*.puml
$ csdflint < examples/valid/client.puml
$ csdflint -list-rules
```

The four severities are `ERROR` (definitely wrong), `WARN` (probably not what
the author meant), `HINT` (suspicious, but may well be intended) and
`STYLE_PROBLEM` (about how the source is written, not about what it means).

The output is written for two readers at once: a CI job, which reads the exit
status, and an AI reviewing a diagram it wrote itself, which reads the messages.
So a message says what is suspicious *and what would settle it*.

No rule evaluates an atom: an atom is text a language interprets, and a rule
concludes only what the builtins and the shape of a formula decide. The rules
are:

| Rule | Severity | Reports |
| --- | --- | --- |
| `syntax-error` | `ERROR` | a file the reader refuses, at the line it stopped, or at the line of the edge whose clause it refused |
| `self-transition-divergence` | `WARN` | a `tau` edge on a cycle of `tau` edges the start reaches, so the diagram may diverge |
| `self-transition-post-breaks-guard` | `HINT` | a self-transition whose post does not keep a state variable its guard reads, so it may be two states written as one |

`self-transition-divergence` sets aside an edge whose guard is false on its
face: `@ne(t, t)`, `@eq(a, b)` beside `@ne(a, b)`, `@in(k, m)` beside
`@notin(k, m)`, or `@empty(m)` beside `@in(k, m)`, terms compared as written,
also under an `∃`. Any other `tau` cycle is reported, since only its atoms say
whether it can run forever; `csdflivelockfree` settles that. A self-loop on an
observable event is not divergence and is not reported.

`self-transition-post-breaks-guard` stays silent only when it is sure the post
keeps the guard: every state variable the guard reads is kept by `@eq(v', v)`
or `@frame(v', v)` in the post. An atom reads only its holes, so the guard then
holds again on the same event. A field of the event or a constant the guard
reads is not the state's and needs no keeping. An omitted post keeps nothing.

`csdflint -list-rules` prints every rule with a one-line summary. Lint what a
person wrote: the expansion of a promotion is one state with many self-loops by
construction, so linting the output of `csdfpromote` says only that.

## Livelock freedom

`csdflivelockfree` compiles a livelock-freedom proof obligation for a single CSDF
diagram and exits 0. Livelock freedom — no divergence: no reachable cycle of internal
`tau` transitions that can actually run forever — depends on the environment the clauses
name (atoms, functions and types; see [CLAUSE_DESIGN.md](./docs/CLAUSE_DESIGN.md)), which
this tool does not interpret. So rather than decide the verdict via exit status, it emits
a proof obligation, to be discharged downstream. It reads the clause syntax of
[SYNTAX.md](./docs/SYNTAX.md), so the expansion of `csdfpromote` can be piped into it.

The output format is chosen with `-target`:

- `ir-json` (default) — a prover-agnostic JSON obligation IR.
- `isabelle` — an Isabelle/HOL proof-obligation skeleton.
- `lean` — a Lean 4 proof-obligation skeleton.

```console
$ csdflivelockfree examples/valid/vending_machine.puml
{"structurally":true,"states":[...],"init":"vmIdle","init_post":{...},"edges":[...],"ends":[],"lemmas":[],"assumptions":[]}
$ csdflivelockfree -target lean examples/valid/vending_machine.puml
$ csdflivelockfree -target isabelle examples/valid/vending_machine.puml
$ csdfparallel a.puml b.puml | csdflivelockfree -
$ csdfpromote examples/promote/TRADES.puml | csdflivelockfree -target lean -
```

The JSON IR lists the states with their variables, the start state and the post of the
start edge, and each edge with the fields its event receives and its guard and post as
one formula: the syntax tree of the formula of logic the clauses state (`step`), whose
atoms, builtins and quantifiers are those of the clauses. `lemmas` are what the `csdf_*`
predicates the builtins become mean, for those the clauses use; the skeletons prove them. `structurally` is `true`
when no reachable `tau` cycle exists, in which case the obligation holds whatever the
clauses say. Options precede the file; a file argument, a `-` argument, and stdin are all
equivalent.

For the `isabelle` and `lean` targets, the skeleton declares the state space as an ADT, an
`init` predicate on the start state, a `step` relation over every transition, an
inductive `reachable`/`Reachable` predicate (the states `init` holds of, closed under
`step`), and a `tau_step`/`tauStep` relation over the `tau` transitions only. It then
states the livelock-freedom theorem — well-foundedness of the `tau` relation **restricted
to the reachable states** — left as `oops`/`sorry`. The restriction matters: the state ADT
also holds valuations the diagram can never enter, and a `tau` cycle among those would make
the unrestricted theorem false even for a diagram that is livelock free. Isabelle uses
`wf_on {s. reachable s} …`; Lean folds `Reachable s` into the relation instead, which is
equivalent because `Reachable` is closed under `step`. When the diagram is structurally
livelock free the obligation is already discharged, so only a note is emitted instead.

The clauses are spelled, not left opaque. Every value is of one datatype `val`/`Val`, and
names are encoded behind a prefix of their kind, so that no CSDF name meets a keyword or a
name the skeleton declares:

| Clause | Spelled as |
| --- | --- |
| an atom, `$n > 0` | `atom_<text> v_n`, an uninterpreted predicate named by its text with `$_i` marks, applied to its holes |
| a function of the environment, `${f($x)}` | `fn_<name> v_x` |
| an entry of a map, `m[k]`, and a field, `r.f` | `csdf_index v_m v_k`, `field_<f> v_r`; a clause reading an entry is conjoined with `csdf_in v_k v_m` |
| `@eq`, `@ne` | `=` and its negation |
| `@in`, `@notin`, `@empty`, `@update`, `@frame`, `@at` | `csdf_in`, its negation, `csdf_empty`, `csdf_update`, `csdf_frame<n>` (n keys), `csdf_at` |
| `@exists(k : T) (…)` | `∃k. type_<T> k ∧ …` |
| a state variable `x`, a value after the step `x'` | `v_x`, `v_x_u27u` |

A state variable and a received field are of the type named like them, the convention
until they carry types of their own, so the `step` relation chooses each of their values
from its type. The atoms, functions and types are the environment: each is declared —
`opaque` in Lean, `consts` in Isabelle — under a `TODO(csdf)` marker and a comment carrying
the text it was named by, for a human or LLM to define and then discharge the proof.
Nothing is defined as True on the diagram's behalf, because that is not a placeholder but a
different diagram, one where every guard holds.

The builtins are no assumption: each is defined, and what it means is proved. A map is a
`ValMap`, a list of its entries, and maps nest. A value is well formed (`csdf_wf`) when every
map in it has distinct keys, sorted in a linear order of every value the library gives, and
every quantifier over a type is restricted to well-formed values, so that two maps are
equal just when they hold the same entries (`csdf_map_ext`, proved in the file): a map is
represented by exactly one well-formed list, as the prover checks prove.
`csdf_is_map` holds of a map, `csdf_in` and `csdf_index` read its entries, and
`csdf_empty`, `csdf_update` and each `csdf_frame<n>` are defined as their maps being maps
and their meaning holding. An instance is a record whose first component is its state,
and `csdf_at` is that it is the state constant, each a number of its own. What the
builtins mean is then a lemma `csdf_lemma_<i>`, proved in the file from the definitions
(`auto` in Isabelle, a projection of the definition in Lean), which the prover checks: no
theorem rests on an axiom, so none holds by a contradiction among axioms. A bare
`@frame(m', m, k)` says nothing of `k` in `m'`, so it is deliberately nondeterministic on `k`:
`m'` may hold `k` at any value or not at all (two different well-formed successors exist, as
the prover checks prove); a post pins `k` down with `@notin(k, m')` or uses `@update`. The model rests on
the libraries: an Isabelle theory imports `HOL-Library.Countable`, so a session building it
declares `sessions "HOL-Library"` in its ROOT (the ROOT is shown by `csdflivelockfree -h`
and `csdfrefinement -h`), and a Lean file imports
`Mathlib.Data.List.Sort`, `Mathlib.Order.RelClasses` and `Mathlib.SetTheory.Cardinal.Order`,
which need Mathlib `v4.29.0-rc4` (Lean `v4.29.0-rc4`, the version lean-csp-prover pins) or later. An assume note of the
diagram (see [SYNTAX.md](./docs/SYNTAX.md)) — what it assumes of its runs as a whole, such as
"a transaction whose fee keeps being raised is eventually confirmed", which no guard can
state — is listed under `assumptions` in the IR and becomes an uninterpreted proposition
`assume_<id>` in the skeletons, under which the theorem is stated: `theorem
livelock_free (h_assume_fair : assume_fair) : …` in Lean, `assumes "assume_fair" shows …` in
Isabelle. That is where a fairness
assumption belongs: a `constrain` would refuse the step, which is a different system.

The obligations checked in as `examples/Livelock_Obligation.{lean,thy}` were filled in by
hand from the encoding of an earlier release, in which every clause was an opaque
predicate.

## Trace checking

`csdftracechk` checks whether an event sequence is a trace of a diagram in the
stable-failures sense. The sequence is a TSV whose header is the single column
`event` and whose every other row is one visible event (`tau` cannot appear).
It is read as CSV with a tab delimiter, so a field may be quoted to hold a tab
or a newline, and blank lines are skipped. Any number of such files may be given after the diagram, and the
diagram may be `-` for standard input. When there are too many traces for the
command line, list their paths in a TSV whose header is the single column `path`
and pass it with `-traces`; the listed traces are added to those given as
arguments, relative paths are relative to the working directory, and the list
may be `-` for standard input unless the diagram is.

```console
$ csdftracechk examples/valid/vending_machine.puml trace.tsv
$ csdftracechk -match prefix examples/valid/vending_machine.puml trace1.tsv trace2.tsv
$ csdfparallel -sync 'insert' a.puml b.puml | csdftracechk - trace.tsv
$ (echo path; find traces -name '*.tsv') | csdftracechk -traces - examples/valid/vending_machine.puml
```

The reading is the one under which an environment offering the events one at a
time is guaranteed to have each accepted: after every prefix of the trace, no
stable state the diagram may have reached by performing it refuses the next
event. So with `A --> B : 1`, `A --> C : 1` and `C --> D : 2`, the sequence
`1, 2` is rejected: after `1` the diagram may be in `B`, which is stable and has
no edge for `2`. Under the plain traces reading the branch through `C` would
have carried it, but a tester driving the diagram cannot choose that branch.

The check first takes every guard as true, following `tau` edges silently and
keeping every state a nondeterministic diagram may be in. If some stable state
reachable after a prefix has no edge for the next event, the Markdown report
says which prefix, which states, and along which paths the refusing state is
reached, and the tool exits 1. Since a path may be blocked by a guard the tool
cannot read, it also states the condition under which the refusal is not real:
every such path is infeasible, i.e. the clauses along it cannot all hold.

Otherwise, for every event of the trace and every path performing the prefix
before it (`tau` steps included), the report tabulates the guards and posts
along the path and states the obligation over the clauses themselves, spelled
as formulas (see [SYNTAX.md](./docs/SYNTAX.md)):

```
∀ v@0 k#1 v@1 … . start(v@0) ∧ step_1(v@0, k#1, v@1) ∧ … → unstable(v@i) ∨ enabled(v@i)
```

where `v@i` is the value of the state variable `v` after step `i` (the start
edge's being step 0) and `k#i` the field `k` step `i` receives. A sent field is
no variable of its own, since it is a value the step has bound. The fields
occur only in the premise, so binding them universally makes the obligation
hold for every value the environment offered and every value a hidden field
took on the way. `unstable(v@i)` says some `tau` edge out of the state reached
is enabled — its guard holds and its post admits values after it — and
`enabled(v@i)` says some edge for the event is, for some values of the fields it
receives. A trace names no
value, so its event is performed when some value is accepted; that the post
admits a successor for every accepted value is not asked. The
report ends with a prompt asking a reader, a person or an LLM, to decide
whether every obligation holds. As with the other checkers the atoms are not
evaluated, so the tool never decides that itself: exit 0 means only that
every trace passed the all-guards-true check. A path never revisits a state
within one run of `tau` edges, so a `tau` cycle yields finitely many paths and
the ones going round it are not listed; a FAILS answer to the prompt therefore
settles that the sequence is not a trace, while HOLDS settles it only for the
listed paths. Divergence is not checked here; that is `csdflivelockfree`'s job.

A trace event is text, so it is looked up in the diagram by one of two simple
rules chosen with `-match`. `exact` (the default) accepts it as an event of a
diagram's edge when it is of the edge's channel and has a field of each
direction in order, each written `?x` or `!x`, where `x` is the field's name or
the value it carries, which the check does not read: `insert?coin` and
`insert?3` are both the event of `insert?coin`. `prefix` accepts it when it is
that of the channel and of the first fields, stopping at the boundaries of each,
so a trace whose fields were stripped (`insert`) matches `insert?coin`, and
`ins` matches nothing. Anything richer, such as
stripping the parameters of some events but not others, is best done to the TSV
beforehand:

```console
$ qhs -t -H -T -O 'select case when event like "choose?%" then event
    when instr(event, "?") > 0 then substr(event, 1, instr(event, "?") - 1)
    else event end as event from trace.tsv' > stripped.tsv
$ csdftracechk -match prefix examples/valid/vending_machine.puml stripped.tsv
```

A trace event matching several edges is nondeterminism: every branch must be
able to go on.

## State transition table

`csdftranstable` writes the state transition table of a diagram as TSV: a row
per reachable state, a column per event, and in every cell what may happen when
the environment offers that event in that state. A diagram shows where each
event goes; the table shows, just as plainly, where it is refused, so that
"this state should not refuse that" is easy to notice.

```console
$ csdftranstable examples/valid/vending_machine.puml
$ csdftranstable -expr-mode logical examples/valid/vending_machine.puml
$ csdftranstable -conditions enabling examples/valid/vending_machine.puml
$ csdftranstable -format json examples/valid/vending_machine.puml
$ csdfcomp tree.json | csdftranstable -
```

For `vending_machine.puml` it writes this table (shown here as Markdown, with
a line break for each line of a cell):

| state | name | showAvailable!availableProducts2 | insert?coin | showPurchasable?purchasableProducts | choose?product | drop?product |
|---|---|---|---|---|---|---|
| vmIdle | vmIdle | [availableProducts2 = availableProducts and "$_0 is $_1"(availableProducts', availableProducts)] → vmIdle<br>[not (availableProducts2 = availableProducts)] × | ["$_0 is the set of $_1"(coins', coin) and "$_0 is $_1"(availableProducts', availableProducts)] → vmCoinsInserted | × | × | × |

| vmWaitingChoosing | vmWaitingChoosing | × | ["$_0 is $_1 with $_2 added"(coins', coins, coin) and "$_0 is $_1"(availableProducts', availableProducts)] → vmCoinsInserted | × | ["$_0 contains $_1"(availableProducts, product) and "$_0 is $_1"(dispensing', product)] → vmDropping<br>[not "$_0 contains $_1"(availableProducts, product)] × | × |

The columns are `state` (the ID), `name`, the visible events, and `[*]` when a
reachable state has an end edge. States come in the canonical order, sorted by
their IDs, and events in the order the states and their edges come, so the
same diagram always gives the same bytes. A column is an event: its channel and a
field of each direction in order (see `docs/SYNTAX.md`), whatever an edge names
its fields, so `insert?coin` and `insert?c` are one column. The column names
each of its fields after the first edge's, made fresh where that name is taken
by a state variable or by another position (`showAvailable!availableProducts2`
above), and each edge's clauses are read with its received fields renamed to
the column's and, for each field it sends, the condition that the column's
value there is the one it sends.

A cell holds one outcome per line, `[C] → s` (the event may be accepted, and
the diagram be in `s`) or `[C] ×` (the event may be refused), each when its
condition `C` holds; a line without one happens unconditionally. Every line
holds on its own, so a cell is the set of what may happen, and several edges
for one event are simply several lines, whether their guards exclude one
another or not. A multi-line cell is quoted, as CSV quotes it.

`C` is a formula of first-order logic: the guards and posts along its way,
spelled as the formulas their clauses are (see `csdflivelockfree`), each atom
quoted as a JSON string so that no text it holds reads as a connective and
applied to its holes. The variables are

| variable | stands for |
|---|---|
| `v` | the state variable `v` of the row's state |
| `k` | the field `k` the column's event receives, as the environment offers it |
| `v'` | the variable `v` of the state an accepted event leads to |
| `v@i` | the variable `v` after the `i`-th `tau` step |

A line in the column of `insert?coin` speaks of the `coin` offered, so a
refusal is one of that value, as a stable failure refuses events with their
values. A field a `tau` hides is bound by the `exists` hiding wrote, inside its
clauses.

The reading is the stable-failures one that `csdftracechk` and
`csdfrefinement -m f` use. The environment cannot see `tau`, so `tau` is not a
column: the diagram may take any number of `tau` edges first, and an outcome
reached that way conjoins every guard and postcondition along the way, in
order, binding with `exists` the values in between, which the diagram
chooses. A refusal happens where the diagram
is stable and cannot perform the event: no `tau` edge is enabled, and no edge
for the event is. With `A`, `B`, `C` and `D` each holding `n`, and
`A --> B : tau ; h1 $n ; p1 $n' $n`, `B --> C : tau ; h2 $n ; p2 $n' $n` and
`C --> D : a?v ; g $v $n ; q $n' $v $n`, the cell of `A` under `a?v` is

```
[not "h1 $_0"(n)] ×
[exists n@1. "h1 $_0"(n) and "p1 $_0 $_1"(n@1, n) and not "h2 $_0"(n@1)] ×
[exists n@1 n@2. "h1 $_0"(n) and "p1 $_0 $_1"(n@1, n) and "h2 $_0"(n@1) and "p2 $_0 $_1"(n@2, n@1) and "g $_0 $_1"(v, n@2) and "q $_0 $_1 $_2"(n', v, n@2)] → D
[exists n@1 n@2. "h1 $_0"(n) and "p1 $_0 $_1"(n@1, n) and "h2 $_0"(n@1) and "p2 $_0 $_1"(n@2, n@1) and not "g $_0 $_1"(v, n@2)] ×
```

where the lines come in the order of a depth-first walk along the `tau` edges:
the diagram may stop and refuse in `A`, in `B` or in `C`, whichever it is
stable in. A variable is bound in step order. The spelling is that of `csdf/logic`, which
`csdftracechk` shares: negation binds tightest; a conjunction and a
disjunction have no precedence over each other, so one inside the other is
parenthesised; an implication binds loosest; and a quantifier reaches to the
end of what it is in, so it is parenthesised exactly when something follows
it.

An omitted guard or postcondition is dropped from a conjunction, and so is a
bound variable nothing reads any more; both are equivalences of first-order
logic, since every set of values is inhabited. An omitted postcondition still
leaves the values after it free, which the variable says. With
`examples/promote/local/CYCLE.puml`, where counting ends by a `tau`, the
counting state both accepts and may refuse `BOOK`, and its `REPORT` is
unconditional because the `tau` and the `REPORT` edge are both omitted
throughout:

| state | name | BOOK?数量 | REPORT |
|---|---|---|---|
| cycIdle | 未開始 | ["total は 数量"(c, x, x')] → cycCounting | × |
| cycCounting | 集計中 | ["total' = total + 数量"(c, x, x')] → cycCounting<br>× | → cycIdle |
| cycFixed | 確定済み | × | → cycIdle |

`-expr-mode` chooses the spelling of the connectives: `natural` (the default:
`and`, `not`, `exists`) or `logical` (`∧`, `¬`, `∃`). Lines that come out the
same, such as those of two `tau` paths that meet again, are written once.

`-conditions enabling` shrinks each condition to what the outcome is enabled
by. It leaves out every postcondition whose values nothing kept after it reads:
that of the accepted event always, and that of a `tau` step unless a later
guard reads the values after the step. Under the premise below such a
postcondition is true once its values are bound, so a condition holds of `c`
and `x` exactly where the full one holds for some `x'`, and only no longer says
what the values after are. For
`vending_machine.puml` the cells above become

| state | name | insert?coin | showAvailable!… | showPurchasable?… | choose?product | drop?product |
|---|---|---|---|---|---|---|
| vmIdle | vmIdle | → vmCoinsInserted | → vmIdle | × | × | × |
| vmCoinsInserted | vmCoinsInserted | × | × | → vmWaitingChoosing | × | × |
| vmWaitingChoosing | vmWaitingChoosing | → vmCoinsInserted | × | × | ["availableProducts contains product"(c, x)] → vmDropping<br>[not "availableProducts contains product"(c, x)] × | × |
| vmDropping | vmDropping | × | × | × | × | → vmIdle |

In the `tau` example above, `"p2"(c2, x1, x2)` stays, since `"g"(c, x2)` reads
`x2`, and `"q"(c, x2, x')` goes. `-conditions full`, the default, keeps every
guard and postcondition.

`-format json` writes the table as JSON, for a program that is to take the
conditions apart, for instance to number them and move them into footnotes,
without parsing a notation back:

```json
{"columns": [{"kind": "event", "event": "choose?product"}, {"kind": "termination"}],
 "rows": [{"state": "vmWaitingChoosing", "name": "vmWaitingChoosing", "cells": [
   [{"result": "goto", "state": "vmDropping",
     "condition": {"op": "atom", "name": "availableProducts contains product", "quoted": true, "terms": [{"op": "var", "name": "c"}, {"op": "var", "name": "x"}]}},
    {"result": "refuse",
     "condition": {"op": "not", "operands": [{"op": "atom", "name": "availableProducts contains product", "quoted": true, "terms": [{"op": "var", "name": "c"}, {"op": "var", "name": "x"}]}]}}],
   [{"result": "terminate", "condition": {"op": "true"}}]]}],
 "unreachable": []}
```

(shortened and laid out by hand). A cell lists its outcomes in the order of
the columns, as the TSV does; `result` is `goto` with `state`, `terminate` or
`refuse`; and `condition` is the syntax tree of `csdf/logic`, whose `op` is
`true`, `false`, `atom` (with `name`, `quoted` and `args`), `not`, `and`,
`or`, `implies` (with `operands`), `exists` or `forall` (with `vars` and
`operands`). Whether an atom is a guard or a postcondition is told by what it
is applied to: a guard reads two variables, or one for an end edge, and a
postcondition three. The lists of the table, of a row and of a cell are
lists, never `null`, even when empty; in a tree, a field its `op` has no use
for is absent, and so are the `args` of an atom applied to nothing and a
`quoted` that is false. Columns are told apart by `kind`, so no event clashes
with one, and `-expr-mode` does not apply. The encoding carries no version of
its own: like the rest of the output, it is that of the `csdftranstable`
release, as `-version` prints it.

The table rests on one premise: every postcondition admits some values after
its step, whatever the parameters and the values before. Under it an edge is
enabled exactly when its guard holds, for some parameters of a `tau` edge or
for those offered, which is what the refusals say; a postcondition no values
satisfy would make a refusal the table does not show. As elsewhere, the guards
and postconditions are natural language and are never evaluated, and whether
the guards of a cell cover every case is left to the reader. The table says
nothing about what the diagram may refuse after a trace, which is
`csdftracechk`'s business.

A diverging state never becomes stable, so it refuses nothing in the
stable-failures sense although it accepts nothing either; a table would show it
as never refusing. So a diagram with a reachable `tau` cycle is refused with the
cycle named, by the same structural check `csdflivelockfree` makes. The guards
are not read, so a cycle they would cut short is refused too. Unreachable
states take no part in the behaviour, so they have no row, their events no
column, and their IDs are written to standard error. A state an edge names but
the diagram never declares has no name and no state variables to tabulate, so
it is an error. An event spelled
`state`, `name` or `[*]` would be read as the column of that name, so in TSV it
is an error. For a promotion, tabulate the local diagrams: the expansion is one state
with a self-loop per local edge.

## Refinement

`csdfrefinement` compiles a refinement proof obligation for two CSDF diagrams and exits 0.
The first is the Spec (the abstract side) and the second the Impl (the concrete side), and
the obligation states that every behaviour of the Impl is allowed by the Spec — the
direction FDR checks. It reads the clause syntax of [SYNTAX.md](./docs/SYNTAX.md). As with
`csdflivelockfree`, whether it holds depends on the environment the clauses name, so the
exit status never encodes the verdict.

The model is chosen with `-m`, which is mandatory because each model is a different claim:

- `t` / `trace` — trace refinement.
- `f` / `stable-failure` — stable-failures refinement, which subsumes traces.
- `fd` / `failures-divergence` — failures-divergences refinement.

The output format is chosen with `-target`: `ir-json` (default), `isabelle` (an Isabelle/HOL
theory importing [CSP-Prover](https://github.com/yoshinao-isobe/CSP-Prover)), or `lean` (a
Lean 4 file importing `lean-csp-prover`, the Lean translation of the same library). The two
prover skeletons mirror each other declaration for declaration, so they can be read side by
side.

```console
$ csdfrefinement -m t abs.puml detail.puml
{"version":2,"mode":"trace","alphabet":[{"name":"a","arity":0}],"spec":{...},"impl":{...}}
$ csdfrefinement -m fd -target isabelle abs.puml detail.puml
$ csdfparallel a.puml b.puml | csdfrefinement -m f abs.puml -
```

At most one argument may be `-`: two diagrams cannot be told apart in a single stream.

The prover targets encode both diagrams as CSP-Prover process terms and state the
obligation as a one-line `<=T`/`<=F` refinement, so the artifact stays small and the
metatheory that makes it meaningful is CSP-Prover's rather than this tool's. An event
carries the value of each of its fields, in order: an event of a channel is the channel
applied to them, so `inc?k` with `k = 1` and with `k = 2` are two events, and a channel
with one number of fields in one place and another elsewhere is refused. Each state
becomes a process name — parameterised by its variables — whose body is the external
choice over its out-edges. Each edge is an external prefix choice `? ev:X -> …` over the
events it is *enabled* for: those of some received values of their types for which some
values after it pass its guard and post, so an edge no valuation lets fire contributes a
refusal (the choice over the empty set is `STOP`). The successor is a replicated internal
choice over the values after it that the event, the guard and the post admit, since the
diagram — not the environment — picks one. A `tau` edge becomes a prefix on the reserved
event `HTau`, hidden once at the outermost level, which is what produces instability and,
on an infinite `tau` run, divergence. An end edge becomes `IF <guard> THEN SKIP ELSE STOP`.
The start edge becomes the replicated internal choice over the initial valuations its post
admits; when it admits none that choice is over the empty set, which is `DIV` — a diagram
that cannot start diverges. A diagram without state variables follows the same rule.

The clauses are spelled as `csdflivelockfree` spells them (see the table above): only the
environment — atoms, functions and types — is declared uninterpreted, once for both
diagrams, under a `TODO(csdf)` marker, so formalising it once serves every obligation it
appears in. Defining it as `True` instead would not be a placeholder but a different
diagram, one in which every guard holds, so the theorem could be discharged for diagrams
that do not refine one another; treat an artifact that still carries a `TODO(csdf)` marker
as undischarged. The builtins are defined and what they mean proved, as for
`csdflivelockfree`. The refinement is stated under no hypothesis, and so is
`initialisable_S`/`_I`, stated in every model: of the
Impl it is what keeps the refinement from holding vacuously, since an Impl that cannot
start is `DIV`, and it must not rest on what the Impl assumes; of the Spec it is a sanity
check, which may fail to prove when the Spec can start only under its assumptions — that
is expected, not a flaw of the encoding. Each side's assume notes, side-qualified (`assume_<id>_S`, `assume_<id>_I`), are
hypotheses only of that side's livelock-freedom under `-m fd`, so the FD conclusion is
conditional on the Impl's assumptions. An assumption of the Impl could make the refinement
hold vacuously, and one of the Spec is typically about liveness, which traces and stable
failures cannot state (see [CLAUSE_DESIGN.md](./docs/CLAUSE_DESIGN.md)). Process names are side-qualified (`S_<state>`, `I_<state>`), because state names
collide between the two files.

CSP-Prover has no failures-divergences model, so `-m fd` emits the standard reduction: for
divergence-free processes FD refinement coincides with `<=F`, so the theory carries a
divergence-freedom obligation per side — the `csdflivelockfree` obligation inlined, in its
`wf_on` form, since the F model cannot observe divergence at all — plus the
initialisability obligation of each side, since `DIV` diverges on the empty trace and no
`tau`-step argument rules that out, plus the stable-failures refinement. A side that is structurally livelock
free gets a note instead of the `wf_on` theorem. The divergence-freedom obligations are
stated under that side's assumptions. Requiring both of the *Spec* is stronger
than FD refinement needs — `DIV` is the bottom of the FD model, so `Spec ⊑FD Impl` holds
even for a diverging Spec — but `<=F` cannot see that, so `-m fd` cannot decide a
refinement whose Spec side diverges.

One encoding detail is forced by the prover rather than by CSP. A replicated internal
choice can only be indexed by the event type there — the process datatype has no spare type
variable — so the event type is layered into `Alphabet` plus an inert `Internal` index, reached through the library's injection-based
replicated choice. No process ever performs an `Internal` event, so no trace and no refusal
changes.

Checking the generated theory needs CSP-Prover. Upstream is pinned to Isabelle2020, so
use the Isabelle2025 fork at `github.com/Kuniwak/CSP-Prover`, which builds against the same
Isabelle the `csdflivelockfree` skeletons target:

```
$ isabelle build -d path/to/CSP-Prover -b CSP_F
$ isabelle build -d path/to/CSP-Prover -d . <your session>
```

The Lean skeleton needs `github.com/Kuniwak/lean-csp-prover` and its pinned toolchain
(`lake exe cache get && lake build`, then `lake env lean path/to/Refinement_Obligation.lean`).

`csdf/obligationir/provercheck` runs both provers over a corpus of generated obligations,
so this is checked rather than assumed — the backend golden tests compare strings and
cannot tell a well-formed theory from one that does not parse. It skips unless pointed at
the libraries:

```
$ CSDF_LEAN_CSP_PROVER=path/to/lean-csp-prover \
  CSDF_CSP_PROVER=path/to/CSP-Prover \
  go test ./csdf/obligationir/provercheck/
```

`CSDF_ISABELLE` names the `isabelle` executable when it is not on `PATH`.
`CSDF_REQUIRE_PROVERS` names the provers whose absence is a failure rather than a skip
(`lean`, `isabelle`, `all`, or a comma-separated list), which is how each Provers job
avoids passing without checking anything.

## Compiling the obligation IR separately

`obligationirc` is the same IR compiler as a standalone tool: it reads the JSON IR (from
`csdflivelockfree`, or a file) and compiles it with the same `-target` values. So these
are equivalent:

```console

```

## Bounded model checking

`csdfbmc` decides the properties the other tools can only state as
obligations, by walking the reachable states of a diagram over *finite*
types. The checker is a Python package (standard library only, Python 3.11
or later); the `csdfbmc` binary of a release carries its sources and runs them
with the `python3` on the PATH (or the one named by `-python` or
`$CSDFBMC_PYTHON`), unpacking them once per version under `$CSDFBMC_CACHE` or
the user cache directory, so nothing has to be checked out. The Go tools own
the structure: `csdfparse` prints a diagram as JSON with its clauses as
formulas, and `csdfpromote -format json` prints an expansion the same way.
The checker owns the values: it evaluates the builtins and `∃` itself, reads
every atom through a *glue* of the atom's language, and takes the types, the
functions of the environment and what to check besides from a *checks
module*.

```console
$ csdfparse examples/bmc/withdraw_formal.puml > withdraw_formal.json
$ csdfbmc withdraw_formal.json examples/bmc/withdraw_formal_defs.py \
    --evaluator-module "csdfbmc.python_glue examples/bmc/withdraw_formal_defs.py"
states: 22
deadlock ×3 at sending after 出庫; first after ['出庫(数量=3)']
```

The checker knows no language by name: it reads every atom through a glue,
a long-running program that speaks the evaluator protocol on its standard
input and output, one JSON request and one JSON answer per line. A request
carries an atom as the glue receives it — `{"text": [...], "holes": [...],
"primed": [...]}`, the text without its holes, the argument each hole reads,
and which arguments are values after the step — and the values of the
arguments by index, never a name. A glue answers `hello` (its language and
protocol version, 2), and `guard` and `post`: a guard atom's truth value per
list of values, and a post atom's lists of values after the step per list
of values before it, one value per primed argument. An optional `symmetric`
request is listed in `hello` by a glue that answers it. Values are tagged
JSON (`{"tuple": …}`, `{"set": …}`, `{"map": [[k, v], …]}`), since JSON has
none of them. An instance of a family reaches a glue as the map of its
fields: its local state is a position, which only the builtin `@at` reads.
Atoms must be pure: the checker asks about an atom once per list of values.
`csdfbmc/protocol.py` states the protocol in full. Anyone may add a language
by writing a glue; `--evaluator CMD` starts it, and `--evaluator-module
MODULE` loads a glue written in Python in-process, with no round trip. One of
the two is needed. Protocol 1, which named clauses and asked `analyse` and
`beyond`, is no longer spoken.

The reference glue, `csdfbmc.python_glue`, reads an atom as a pure subset of
Python — an expression; no assignment inside a function, no loop statement,
no exception, no I/O, no randomness, no float — whose holes are names of
their own, so that evaluating an atom is deterministic. A guard atom is any
expression (`$残高 >= $数量`); a post atom is `$x' == e`, `$x' in e`, or a
tuple of every value after the step on the left, where `e` reads none of
them (`$残高' == $残高 + $額`). An atom that is not Python of the subset is
an error. The glue's arguments are modules whose public names every atom
may use, checked against the same pure subset.

A post is solved, not searched. The values after the step come from what
determines them: an equality builtin with a value after the step on one side
(`@eq(残高', 残高)`), `@empty`, `@update`, `@frame` with `@at` and `@notin`
for its keys, and the values a post atom allows. A variable nothing in the
post determines ranges over its type in `TYPES`, and is refused without one;
every valuation is then checked against the whole post, so two clauses that
disagree admit no successor. A clause that reads an entry its map does not
have (`m[k]` with `k` not in `m`) is false, never a default value. A field
an event receives ranges over its type, except one an equality of the guard
determines from the state and the fields before it (`@eq(x, n)`), which is
computed, whatever its type holds. A sent field (`c!y`) sends the value `y`
has at the step. A field hidden by `csdfhide` is bound by `∃` in the guard
and the post, and ranges over the type the `∃` names.

The checks module is Python too, checked against the same subset before it is
imported. `TYPES` maps a type to the finite set of its values (its carrier
set), and a name ranges over the type of its own name; `TYPEOF` maps a name
to another type, so that `相手ID` can range over `口座ID`
(`TYPEOF = {"相手ID": "口座ID"}`). `csdfbmc.values.record(field=domain, …)`
and `partial_map(keys, values, max_size)` enumerate a type of records or
partial functions from the types of the fields and a bound on the number of
keys. `csdfbmc.values.sample(values, beyond=[…])` gives a type as a sample
of a larger one (`TYPES = {"試行ID": sample(["t1", "t2", "t3"],
beyond=["t4"])}`): the walk ranges over the values listed, and the type has
more, of which `beyond` lists at least one, written like any value of
`TYPES`; a plain list is the whole type. Loading refuses an empty `beyond`
and a value of `beyond` that is one of the sample's.
A module that defines `DOMAINS` or `CLAUSES`, which an earlier
`csdfbmc` read, is refused.

Which atoms are functions of the environment (docs/CLAUSE_DESIGN.md, P15 and
P16) is declared by the checks module alone: every key of `ENVIRONMENT`
declares one, and every other atom is the glue's. A function is named as
the diagram's JSON names it (an atom's `function`): the atom's text with
each hole written as the position of the argument it reads, so
`$口座 が凍結されていない` is the function `$_0 が凍結されていない` of the
value of `口座`, and every atom with that text, on any edge and in a guard
or a post alike, is the same function. A key names a function so, and
`csdfbmc` never reads an atom's text itself. A key gives the function `True`,
`False` or a pure function taking the arguments in order, or `None`, which
declares it and leaves it to `--env NAME=true|false`. `--env` may name only
a declared function. A function is given, never chosen: there is no
`--seed`, for a function chosen at random is a structureless predicate that
says no more than the guards left unknown; a pseudo-random function, if
wanted, is written in `ENVIRONMENT` (with `hashlib`, say). A post
atom the environment decides is decided for each value of its types after
the step. A key of `ENVIRONMENT` may also give an environment function a
term applies (`${f(x)}`), by its name, as a pure function of the values.
Before the walk, csdfbmc refuses a declared function nothing gives, listing
every one, and a declared name that names no atom of
the diagram; nothing is approximated. The report names the given
functions and the ones an atom was decided by (`environment` in `--json`),
which is what reproduces a run.

Three more tables are optional. `INVARIANTS` maps a name to a predicate over
the state variables and ghosts it reads; it is checked at every reachable
state that binds all of them, and a state that breaks it is reported with
its trace. `GHOSTS` maps a name to `(initial value, {event name: update})`: a
value the diagram does not keep — a running total, a count — that follows
the events. An update reads the ghosts, the event's fields and the state
variables before the step and returns the new value; a ghost with no update
for an event keeps its value. Ghosts are part of the state the walk tells
states apart by, so a total that grows without bound is cut by
`--max-states`. A ghost update and an invariant see an instance as the map
of its fields. `SYMMETRIC` lists the types whose values `--symmetry` may
rename.

The walk is breadth-first over (control state, valuation, ghosts) triples, up to
`--max-states`. It reports every reachable state with no enabled transition and
no end edge whose guard holds as a deadlock, with the trace that reached it,
and every cycle of `tau` transitions among the reachable states as a tau
cycle. With `--avoid EVENT` it also reports every cycle among the reachable
states that never performs that event: under a fairness assumption written
as a finite bound (a resend count in the types), such a cycle is a run that
never gets to the event, which is the livelock the `assume` note was about.
It also reports every (state, event) where the guard held but the post
admitted no successor ("post admits no successor"), which counts for the
exit status only as a deadlock it leaves. Findings of one shape are reported
once, with their count and the shortest trace: deadlocks by control state
and the event that led there, broken invariants by invariant and control
state, cycles by the control states they run through, empty posts by event.
`--all` lists every finding; `--first` stops the walk at the first deadlock
or broken invariant (cycles need the whole space and are then not looked
for).

A finite bound can end a run the diagram would go on with: once every ID of
a finite type is used up, nothing is enabled, though a fresh ID would be.
For a type given as a sample, a state with no enabled transition and no end
edge whose guard holds is tried once more, with each sample extended by all
its values `beyond` at once, and every type `record(…)` or `partial_map(…)`
built of the sample built again of the wider one, so that a record whose
field is of the sample also takes them. A type derived some other way, a
comprehension over a sample say, is not widened. If an end edge or an edge
is then enabled, the state is reported as `bound reached … (W is enabled by
a value beyond a sample)`, W the witness: `the end edge`, or the first step
enabled, as taken, with the value beyond it bound — `bound_reached` in
`--json`, each with its `witness`, and a group of kind `bound_reached`. It
is no finding, so it does not set the exit status. Otherwise it is a
deadlock. The values are only tried: the walk adds no state for them, so
the state count is the same.

This is sound with no restriction on how the diagram tells values apart. A
state reported as the bound reached comes with a witness: a value of the
real type that gives the state a way out, so it is not a deadlock of the
real type. A state none of the values beyond gives a way out is reported as
a deadlock, as without the sample, so the state being judged never hides a
real deadlock. This is about that state only: the walk does not go on from
a value beyond the sample, so a deadlock reachable only through such values
is not explored; that is the bound. An
atom may order the values or compare them with constants; a witness it
allows is still a witness. What csdfbmc cannot check is that the values
`beyond` are values of the real type: that is the user's to keep, as it is
that the sample is.

`csdfbmc next <diagram.json> <checks.py> (--evaluator CMD | --evaluator-module
MODULE) (--initial | --state JSON --edge N)` answers what a REPL asks at a
value prompt — the values the clauses admit for the start state, or after the
N-th outgoing edge of a runtime state — which `csdfrepl -checks` and
`csdfrepld -checks` use. `--json` prints the same as JSON, and under every
finding a `replay`: the initial values and, per step, the edge taken (event,
source, destination, line) and the values of the state it leads to, which
`csdfrepl -replay` and `csdfreplcmd replay` walk so the finding can be looked
at in the REPL; an instance is written `{"at": STATE, "fields": {…}}`. The
exit status is 1 when something was found, 2 when the inputs could not be
read.

The first worked example, `examples/bmc/withdraw_formal.puml`, is a two-state
ledger: a transfer is accepted when the balance covers it and completes when
the balance also covers the fee. The explorer reports the states with no way
out and the trace to each; change a clause and the report changes with it.
`withdraw_formal_defs.py` is both its checks module and the module of the
constants its atoms name, given to the glue as an argument.

The second, `examples/bmc/wallet_formal.puml`, is a toy ledger with deposits,
one transfer at a time with a retry, and a fee refund from outside the
balance. It checks six properties at once: no deadlock; no livelock under the
fairness assumption (the `assume` note, which `wallet_formal_checks.py` turns
into the bound `RESENDS`, with `--avoid 確定 --within sending`); and the
`INVARIANTS` over `GHOSTS` that total the events, relating the balance to the
amounts moved and the fees paid and refunded. The run reports a deadlock with
its trace; the comments in `wallet_formal_checks.py` say what to change to
make every check pass.

```console
$ csdfparse examples/bmc/wallet_formal.puml > wallet_formal.json
$ csdfbmc wallet_formal.json examples/bmc/wallet_formal_checks.py \
    --evaluator-module "csdfbmc.python_glue examples/bmc/wallet_formal_checks.py" \
    --avoid 確定 --within sending
```

An expansion of a promoted diagram is walked the same way. A map variable
holds, per instance ID, an instance: its local state, which `@at` reads, and
its local variables, which an atom reads as `${attempts'[試行ID].手数料}`.
Which variables an instance holds at each local state is the family the JSON
writes (`families`): after `@at(m'[k], S)` the instance holds exactly the
variables of `S`, each one the post leaves open ranging over its type in
`TYPES` (refused without one), and a post that gives a field `S` does not
hold, or puts an entry of a map of no family at a state, is refused.
Instance IDs range over the type of the ID field, which is the bound of the
scenario. The third example, `examples/bmc/attempts/`, is the fee-bumping
diagram of `examples/promote/ATTEMPTS.puml` with its atoms written in Python.
A global diagram has no end edge, so the walk stops only once every ID of
the bound is confirmed. The IDs are a sample with `t4` beyond it
(`checks.py`), which lets a new attempt register, so those states are the
bound reached, not deadlocks, and the walk exits 0; no cycle avoids
`CONFIRMED`:

```console
$ csdfpromote -format json examples/bmc/attempts/ATTEMPTS.puml > attempts.json
$ csdfbmc attempts.json examples/bmc/attempts/checks.py \
    --evaluator-module csdfbmc.python_glue --avoid CONFIRMED
states: 496
bound reached ×19 at running after CONFIRMED; first after […] (SEND(試行ID=t4, 未署名Tx={'手数料': 1}) is enabled by a value beyond a sample)
```

`--cone` walks fewer states and finds the same. It leaves out every state
variable outside the cone of influence, which nothing that decides a step
or a property reads: what a clause reads is its free names, the holes of its
atoms and the terms of its builtins, so no glue is asked. A variable is kept
when a guard or an end guard reads it, an invariant or a ghost update names
it as a parameter, an event sends it, it is the map of a family, or a
conjunct of a post reads it before the step; a copy `@eq(x', y)` that is the
only conjunct of its post giving `x` a value reads `y` only if `x` is kept.
A left-out variable is kept at one value, printed `{"left_out": true}` in
`--json`, and the variables left out are listed (`cone of influence leaves
out: …`, `left_out` in `--json`). `csdfrepl -replay` refuses a finding holding a
value left out, since no value of the variable stands for it; run csdfbmc
without `--cone` to replay it. An invariant or a ghost update that takes
any keyword is refused with `--cone`, since what it reads cannot be told.

A reduction keeps the findings, not their counts: the walk reports the
same shapes (a deadlock at a control state after an event, an invariant
broken at a control state, a cycle through control states, …) as without
it, but the number of states, the count of each shape, its shortest trace
and the list `--all` prints are those of the reduced walk. The output says
so in a line naming the reductions used (`reduced by --cone: …`, and
`reductions` in `--json`).

`--por` walks fewer states and finds the same, by partial-order
reduction. An entry `m[k]` of a map is told from the map as a whole, so an
edge moves the instance of `m` at its field `p` alone when every name it
reads or writes is `m` or a field it receives, it writes `m` and keeps
every other variable of its state by a frame `@eq(x', x)` (a variable its
post does not name ranges over its type, and so is written), and every `m`
it names is `m[p]`, `m'[p]`, the membership of `p` or
`@frame(m', m, p)`. In a control state whose edges are all self-loops and
none `tau`, the instances of `m` move independently when every edge writing
`m` moves one alone and updates no ghost, and no other edge, invariant or
ghost update reads `m`. There the walk takes the transitions of one instance
alone, unless one of them is the `--avoid` event or leads to a state already
met (the cycle proviso, which in a breadth-first walk expands a state of
every cycle in full). Deadlocks, the bound reached, broken invariants, empty
posts and cycles are found as without it, of the same shapes. An invariant or a ghost update
that takes any keyword is refused with `--por`. No example of
`examples/bmc` is reduced: in `attempts`, `RESEND` reads the instance it
replaces, which ties the attempts together.

`--symmetry` walks fewer states and finds the same. It stores a state by
the least of its renamings of the IDs, the values of each type the checks
module lists in `SYMMETRIC` (strings, a group per type), and still expands
the state it met first, so every trace is a run of the diagram. It is
refused when anything could tell two IDs apart: a type not closed under
renaming them; an atom the glue says does, asked of every atom with the
arguments that may hold an ID and the maps an ID indexes (the evaluator
protocol's `symmetric` request; a glue that does not answer it is refused);
a function of the environment reading an ID that nothing gives, or
given as Python that does not commute with renaming (tried at load for
every renaming and every value of its arguments' types: renaming the
arguments must rename the result, and leave a truth value as it is); or
the checks module's source naming an ID as a constant (a literal listing
all of a group, as a type does, names none), ordering one, or sorting, or
taking the min or max of, one or a map keyed by them. The builtins and `∃`
never tell IDs apart. What may hold an ID is read from the types and the
builtins; an atom's output is the glue's, so a state in which a variable,
a field or a ghost holds an ID where none was foreseen is refused during
the walk: csdfbmc exits 2 and reports no finding, not even those met
before. Whether the walk meets such a state depends on how far it goes, so
a run within a smaller `--max-states`, or one that `--first` stops early,
may finish where a longer one is refused. The values beyond a sample are
tried at the state as met. `examples/bmc/attempts/checks.py` declares `SYMMETRIC = ["試行ID"]`:

```console
$ csdfbmc attempts.json examples/bmc/attempts/checks.py \
    --evaluator-module csdfbmc.python_glue --avoid CONFIRMED --symmetry
states: 104 (496 without it)
```

In a checkout, `python3 -m csdfbmc` runs the same checker from the sources.
The Python tests run with `python3 -m unittest discover -s csdfbmc/tests -t .`,
and `go test ./...` runs them too when a `python3` is on the PATH.

## Interactive exploration

`csdfrepl` interactively explores one CSDF file:

```console
$ csdfrepl examples/valid/vending_machine.puml
```

The diagram's guards and posts are clauses ([Clauses](docs/SYNTAX.md)); a
diagram holding a clause of the old syntax (`@opaque`, a renaming `@[y := x]`)
is refused with the reader's error. Each value prompt shows the guard and the
post of the pending transition as the clause printer writes them, and an
empty clause as `(none)`.

For each state, enter its variable values as a JSON array in declaration order.
`csdfrepl` checks that they fit the state and, without `-checks`, that no
builtin of the guard or the post (`@eq`, `@ne`, `@in`, `@notin`, `@empty`,
`@update`, `@frame`, `@at`) is false of them and the previous state's values;
a builtin reading an event's field or an environment function is left
alone, and atoms are not evaluated, for only a glue reads them. With
`-checks` (below), the values must be ones `csdfbmc next` admits for the
pending transition. JSON `null` is not accepted. A map of a
family's instances (in an expansion) is a JSON object from IDs to
`{"at": <state>, "fields": {...}}`, as `csdfbmc` writes it: `at` is a state of
the family other than its start state (absence, written by leaving the entry
out), and `fields` holds exactly that state's variables.

Commands use zero-based indexes:

- `l` lists the current state and outgoing transitions.
- `t` displays the current visible trace. The internal event `tau` is hidden.
- `h` displays the exploration history.
- `s INDEX` selects an outgoing transition.
- `e INDEX` takes an end edge (listed under `Ends:`): the run terminates
  there, and only `j` goes on. A builtin of its guard false of the current
  values refuses it; the guard's atoms are not evaluated, even with `-checks`.
- `j INDEX` jumps to a history entry.
- `?` or `help` displays command help.

With `-replay`, the session first walks the path `csdfbmc --json` recorded
under one of its findings and the prompt opens at the state the finding is at,
with the path in the history; `-finding N` picks the finding, numbered from 0
in the order the output lists them (deadlocks, tau cycles, broken invariants,
avoiding cycles, empty posts), then the states where the bound was reached. A step that cannot be
taken, for instance because the diagram changed since the check, is an error.

```console
$ csdfbmc withdraw_formal.json examples/bmc/withdraw_formal_defs.py \
    --evaluator-module "csdfbmc.python_glue examples/bmc/withdraw_formal_defs.py" --json > findings.json
$ csdfrepl -replay findings.json -finding 0 examples/bmc/withdraw_formal.puml
Replayed 1 step(s); the path is in the history.

State: 送信中
...
```

With `-checks CHECKS.py` and a glue (`-evaluator CMD` or `-evaluator-module
MODULE`), every value prompt also asks `csdfbmc` (on the PATH or beside the
binary) what values the clauses admit for the pending transition, shows them
numbered, and takes `#N` in place of the values. `-diagram-json FILE` names the
diagram JSON (`csdfparse`'s, or `csdfpromote -format json`'s for an expansion,
which holds its families) that the session explores and the checker reads in
place of the file.

The environment is csdfbmc's: `-env NAME=true|false` (repeatable) is passed
to `csdfbmc next` as `--env`, so the prompt suggests what csdfbmc walks with
the same given functions. It has no default: a function the checks module's
`ENVIRONMENT` declares and nothing gives is refused at the prompt, as
csdfbmc refuses it. With `-replay`, the prompt walks the environment the
report was made in: its `environment` gives the values its `--env` gave
where `-env` says nothing, and an `-env` value other than the report's, or an `-env` of a function the report's
`--env` did not give, is refused. A report with no `environment`, or whose
`environment` records no `env` (both written by a csdfbmc before 3.0.0,
whose `given` does not tell the checks module's functions from `--env`'s),
is refused; make it again with this release's `csdfbmc --json`. `csdfrepld` cannot take a
report's environment, so it refuses a replay of a report whose `--env`
values are not exactly its own `-env`.

```console
$ csdfrepl -checks examples/bmc/withdraw_formal_defs.py \
    -evaluator-module "csdfbmc.python_glue examples/bmc/withdraw_formal_defs.py" examples/bmc/withdraw_formal.puml
...
Suggested by csdfbmc (enter #N to take one):
  [#0] [3]

state> #0
```

See [CSDFREPL.puml](docs/CSDFREPL.puml) for the behavioral specification.

## Headless exploration for agents

`csdfrepld` is a daemon that holds the same exploration sessions in memory and
serves them over a Unix domain socket, and `csdfreplcmd` is a one-shot client.
Together they let a coding agent (or any script) drive exploration without an
interactive terminal. The client and daemon speak JSONL, one request per
connection.

```console
$ csdfrepld &                                            # listens on $XDG_RUNTIME_DIR/csdfrepld.sock
$ SID=$(csdfreplcmd session new examples/valid/vending_machine.puml)
$ csdfreplcmd read                                       # -s is optional when there is one session
$ csdfreplcmd statevar -json '[0]'                       # enter the current state's values
$ csdfreplcmd select 0                                   # choose a transition, then enter its values
$ csdfreplcmd statevar -json '["done"]'
$ csdfreplcmd trace
$ csdfreplcmd jump 0                                     # branch from an earlier history entry
$ csdfreplcmd end 0                                      # take an end edge: the run terminates
$ csdfreplcmd replay -finding 0 findings.json            # walk a fresh session to a csdfbmc finding
$ csdfreplcmd statevar -pick 0                           # enter the first suggestion (daemon started with -checks)
$ csdfreplcmd read -json                                 # structured output for parsing
$ csdfreplcmd session list
$ csdfreplcmd serverversion                              # the daemon's version
$ csdfreplcmd session rm -s "$SID"
```

The socket path is shared by both binaries via `-sock`, then `$CSDFREPLD_SOCK`,
then `$XDG_RUNTIME_DIR/csdfrepld.sock`, then a temporary directory. Every command
prints human-readable text by default and structured JSON with `-json`, where a
guard or a post is the clause text as the text output shows it (an empty clause
is `"(none)"` in both); `statevar`
instead takes its values via `-json <json-array>` or `-json-file <file>`. A daemon
started with `-checks CHECKS.py` and a glue (`-evaluator` or `-evaluator-module`)
asks `csdfbmc` at every value prompt what values the clauses admit:
`read` lists them under `suggestions`, `statevar -pick N` enters the N-th, and
`session new -diagram-json FILE` names the diagram JSON, on the daemon's side,
that the session explores and the checker reads in place of the file. `-env NAME=true|false` gives every session the environment
csdfbmc walks with `--env NAME=true|false`. The daemon's environment is
fixed when it starts, so `replay` refuses a report whose `environment` it
does not walk: one whose `--env` gave a function another value or a value
the daemon's `-env` does not give, or that did not give a function the
daemon's `-env` gives. Run `csdfreplcmd help` for the full command list.
